# Architecture Charter

## Mission

Provide a single-entrypoint Chief of Staff system that helps users accomplish complex workflows through reusable skills and optional domain agents, while maintaining strict privacy boundaries suitable for open-source distribution.

## Core Principles

1. **One front door.** Users interact with one CoS front door; internal delegation is an implementation detail.
2. **Reactive by default.** The system responds to user requests. No proactive cron, heartbeat, or background behavior unless explicitly enabled by the user.
3. **Schema-driven contracts.** Every skill defines input and output JSON schemas. These schemas are the canonical contract — not prose, not examples.
4. **Evidence over assertion.** Outputs must be grounded in input data. When evidence is insufficient, say so explicitly rather than fabricating.
5. **Privacy by architecture.** Framework and config are exportable. Memory, state, and secrets never leave the local environment.
6. **Minimal viable complexity.** Add agents only when skill-only composition is insufficient. Prefer fewer moving parts.

## System Model

```
┌─────────────────────────────────────────┐
│           Front Door Agent              │
│         (agents/main/AGENT.md)          │
│   Single user-facing conversational     │
│   entity. Owns voice and UX.           │
│                                         │
│   Reads orchestration/skill-registry    │
│   .yaml to discover available skills.   │
├─────────────────────────────────────────┤
│          Orchestration Layer            │
│   orchestration/routes.yaml — routing   │
│   orchestration/skill-registry.yaml     │
│     — auto-generated skill directory    │
├─────────────────────────────────────────┤
│          Domain Agents                  │
│   (agents/<domain>/AGENT.md)            │
│   Internal workers. Own workflow        │
│   orchestration and memory policy       │
│   for their domain.                     │
├─────────────────────────────────────────┤
│             Skills                      │
│   (skills/<name>/SKILL.md)              │
│   Stateless, schema-in/schema-out       │
│   units. No memory, no side effects.    │
├─────────────────────────────────────────┤
│         Memory / State                  │
│   (memory/, state/)                     │
│   Private runtime data. Never exported. │
│   Agents write; skills do not.          │
└─────────────────────────────────────────┘
```

## Skill Discovery

The front door agent discovers available skills by reading `orchestration/skill-registry.yaml`. This file is auto-generated by `scripts/generate-skill-registry.sh`, which scans every `skills/*/SKILL.md` and extracts the `name` and `description` frontmatter fields.

- The registry is the canonical directory of skills. The front door agent should not need to scan the filesystem at runtime.
- The registry is regenerated whenever skills are added, removed, or have their frontmatter updated. See the New Skill DoD in `standards/DEFINITION_OF_DONE.md`.
- The registry file is committed to the repo (it is Config-class data, exportable).

## Single-Entity UX Rule

The user sees and talks to one entity: the Front Door Agent. Domain agents and skills are never exposed directly in conversation. If a domain agent produces output, the front door agent delivers it. Internal routing, delegation, and orchestration are invisible to the user.

## Reactive-First Rule

All routes and agents default to `reactive_only: true`. This means:

- No scheduled runs, cron jobs, or heartbeats are active unless the user explicitly enables them.
- Proactive workflows (e.g., weekly retros) may exist as definitions but must be gated behind explicit user opt-in.
- The system never initiates contact or performs background work without a triggering user action.

## Skill vs Agent Decision Rubric

Use this table to decide whether new functionality should be a skill or an agent:

| Criteria | Skill | Agent |
|---|---|---|
| **Statefulness** | Stateless. No memory reads/writes. | Stateful. Reads/writes memory or state. |
| **Orchestration** | Single-step or self-contained multi-step. | Coordinates multiple skills or multi-turn workflows. |
| **Side effects** | None beyond returning output. | May persist events, update state, trigger other skills. |
| **User interaction** | None. Takes input, returns output. | May require multi-turn interaction (via front door). |
| **Reusability** | High. Designed for use by any agent. | Domain-specific. Tied to a particular workflow. |
| **Failure mode** | Returns schema-valid error output. | May retry, escalate, or degrade gracefully. |

**Default to skill.** Only create an agent when the functionality requires statefulness, orchestration across multiple skills, or domain-specific memory management.

## Data Boundary Rule

| Category | Examples | Exportable |
|---|---|---|
| **Framework** | Standards, skill specs, agent specs, schemas, scripts | Yes |
| **Config** | Route definitions, workflow definitions, templates | Yes |
| **Memory** | Event logs, trend notes, calibration data | No |
| **State** | Runtime state, caches, intermediate results | No |
| **Secrets** | API keys, tokens, credentials, .env files | No |

See `standards/PRIVACY_EXPORT_POLICY.md` for full policy.

## Change Control Rule

Architecture changes (new principles, structural changes to the system model, modifications to this charter) require:

1. **Proposal.** Open a GitHub issue or PR with the proposed change and rationale.
2. **Impact assessment.** Identify which existing skills, agents, and routes are affected.
3. **Review.** At least one review pass before merge.
4. **Migration path.** If the change breaks existing contracts, include a migration guide.

Standards files (`standards/*.md`) follow the same process. Skill and agent additions follow their respective Definition of Done checklists.
